## 1. 项目背景与现状

### 1.1 第二阶段验收成果

根据《DRPD 第二阶段最终验收报告》，第二阶段 M0--M7 已完成：

-   全量自动化测试 159 项通过。
-   纯 Python 协议测试 114 项通过。
-   完整压力测试 7 项通过。
-   新增 48 条酷态科 10 号充电器 Mini 实机 CDC 捕获帧。
-   完成 CDC 到 CaptureRecord、普通 PD 报文、PDO/RDO、VDM/VDO、Extended
    Message 和 EPR 的混合回放。
-   完成 100,000 帧混合回放、100,000 组固定种子随机输入、10,000
    次完整重组及 1,000 次 Reset/Disconnect 周期测试。
-   第二阶段验收版本为上位机 `0.3.1`，分支为 `feature/usb-pd-decoder`。

第二阶段已经形成可供 GUI
消费的捕获记录、解析结果、PDO/RDO、VDM/VDO、Extended Message
和重组结果模型。

### 1.2 实机验证边界

最终验收报告记录了酷态科 10 号充电器 Mini 的 48 条真实 CDC 帧，其中 47
条结构正常的帧通过解析器 CRC 核验。

实机观察包括：

-   5 个 Fixed PDO 和 2 个 PPS APDO。
-   Request、Accept、PS_RDY 控制流。
-   Source_Capabilities_Extended、Status 和 Get_Manufacturer_Info
    三条扩展消息。
-   Identity、SVIDs 和 Modes 发现数据。
-   一条格式异常的 Security_Request，解析器给出
    `invalid_unchunked_header` 和 `extended_length`
    诊断，并拒绝将其发布为完整消息。

报告还指出：DUT 的 EPR 配置为 `ON`，但 EPR PDO 缓存计数为
`0`，实机记录没有出现 EPR Source Capabilities。合规 Unchunked、多块
Extended、Request Chunk、SPR AVS/EPR 请求等仍由构造样本验证。

因此，GUI 必须明确区分：

-   真实捕获并验证过的数据。
-   构造样本验证的数据。
-   部分解析或上下文缺失的数据。
-   格式异常、未知或不支持的数据。

不能将"软件支持某协议格式"显示成"当前连接设备已经实际使用该协议"。

### 1.3 第三阶段目标

第三阶段将第二阶段的协议解析引擎转化为可实际使用的 PySide6
桌面应用，实现：

1.  DRPD 设备连接、断开和状态展示。
2.  USB CDC 实时捕获控制。
3.  实时 PD 报文列表。
4.  原始数据、PD Header 和协议字段详情。
5.  PDO/RDO、VDM/VDO、Extended/EPR 专项分析视图。
6.  协议诊断、过滤、搜索和定位。
7.  原始捕获保存和离线回放。
8.  数据导出和测试记录整理。
9.  与现有电子负载功能兼容。

**本阶段核心原则：协议层保持稳定，GUI 只消费解析结果，不重新实现 USB-PD
协议规则。**

### 2.3 现有电子负载功能的处理原则

本项目名称为"电子负载与 USB-PD
综合测试平台"，因此第三阶段应优先采用增量集成方式：

1.  保留现有电子负载控制、测量和连接功能。
2.  将 USB-PD 协议分析作为新增工作区或功能页面。
3.  不为了新增协议分析页面而重写已经稳定的电子负载控制模块。
4.  设备通信、电子负载控制和 PD 捕获之间通过清晰的 Service 接口协调。
5.  如果当前主窗口已经具备导航、状态栏或设备连接框架，优先扩展现有框架。

## 4. 核心模块实施方案

### 4.1 DeviceService：设备连接管理

职责：

-   获取可用串口/CDC 设备列表。
-   连接和断开 DRPD。
-   显示连接状态。
-   获取设备固件版本和可读取的设备状态。
-   处理设备拔出、连接失败和通信异常。
-   避免重复连接和重复打开串口。
-   向 GUI 发出状态变化信号。

建议状态：

``` text
DISCONNECTED
     |
     v
CONNECTING
     |
     v
CONNECTED
     |
     +------> DISCONNECTING
     |               |
     v               v
ERROR          DISCONNECTED
```

GUI 应展示：

-   设备端口。
-   连接状态。
-   固件版本。
-   捕获状态。
-   最近一次通信时间。
-   最近一次错误信息。

约束：

-   不改变 DRPD 固件数据格式。
-   不在主线程中执行阻塞式串口读写。
-   断开连接时通知 CaptureService 和 AnalysisService 清理对应状态。

### 4.2 CaptureService：实时捕获

职责：

1.  调用现有 DRPD CDC 通信实现。
2.  接收原始 Binary Block。
3.  转换为现有 `CaptureRecord`。
4.  保留原始捕获数据。
5.  按批次向上层提交记录。
6.  统计帧数、错误数和丢失数（仅在有可靠计数依据时）。
7.  支持开始、停止和设备断开处理。

建议接口：

``` python
class CaptureService:
    def start_capture(self):
        ...

    def stop_capture(self):
        ...

    def is_capturing(self):
        ...

    def get_capture_stats(self):
        ...
```

接口仅为职责示例，实际应适配现有代码，不应重复实现已有通信流程。

#### 线程要求

-   CDC 读操作放在工作线程。
-   GUI 主线程只负责控件更新。
-   使用 Qt Signals/Slots 传递批次数据和状态。
-   避免每收到一帧就创建一个独立 QWidget。
-   对 GUI 更新采用批量刷新，避免高频信号导致界面卡顿。

#### 数据积压处理

应设置有界缓冲区，并明确缓冲区满时的行为：

-   优先保证原始捕获记录不被静默丢弃。
-   根据现有传输机制选择暂停读取、背压或记录明确的丢失计数。
-   若无法保证无损，界面必须显示丢失或过载告警。
-   日志中记录缓冲区峰值和丢失情况。
-   不允许只丢弃记录却继续显示"捕获正常"。

### 4.3 AnalysisService：协议分析协调

职责：

-   接收 CaptureRecord。
-   调用现有 `parse_capture(record)`。
-   按原有设计更新 `PDSessionContext`。
-   更新 `VDMContext`。
-   更新 Extended Message Reassembler。
-   生成适合 GUI 使用的分析事件。
-   保留原始结果和诊断。

重要约束：

1.  不在 GUI 控件中调用底层协议位域解析函数。
2.  有状态上下文必须按捕获会话顺序处理。
3.  不允许不同捕获会话共享未清理的上下文。
4.  断开设备、重新开始捕获或加载新文件时，按既有协议规则重置上下文。
5.  同一记录重复解析时，不应意外重复污染上下文。
6.  解析异常应转换为可展示的诊断，而不是使捕获线程退出。

建议输出统一分析事件：

``` python
@dataclass(frozen=True)
class AnalysisEvent:
    record: object
    result: object
    diagnostics: tuple
    session_summary: object | None
```

上面的类型仅表达分层思路；实际字段和类型应引用第二阶段已验收的数据模型，不要为
GUI 复制一套协议对象。

### 4.4 ReplayService：离线回放

职责：

-   打开已保存的捕获文件。
-   读取原始 CaptureRecord。
-   按原始顺序送入 AnalysisService。
-   支持暂停、继续、停止和逐条步进。
-   支持设置回放速度。
-   显示当前进度。
-   回放结束后保留分析结果。

特别注意：

USB-PD 中存在 PDO/RDO、VDM 和 Extended Message
等跨帧上下文。离线回放不能只对用户选中的某一条记录独立调用解析器，就声称恢复了完整会话语义。

建议实现：

-   从文件开头重放，建立完整上下文。
-   第一版暂不提供任意位置无状态跳转。
-   后续若需要快速定位，增加有版本标记的上下文快照或从最近检查点重放。
-   切换文件时清理上一文件的全部上下文。

### 4.5 ExportService：数据保存与导出

第一版建议支持：

  导出类型       内容
  -------------- ---------------------------------------------
  原始捕获文件   保留原始 Binary Block 或 CaptureRecord 数据
  CSV            报文时间、SOP、消息类型、CRC、摘要
  JSON           完整解析结果和诊断信息
  诊断报告       异常类型、帧索引、时间戳和原始数据引用

约束：

-   原始数据导出必须可用于后续重新回放。
-   CSV 只适合表格摘要，不作为完整数据备份。
-   JSON 应包含格式版本。
-   未知字段和原始字节不得在导出时静默丢弃。
-   文件格式应有文档，避免以后版本无法读取旧文件。

-   设备拔出。
-   连接失败。
-   断开后重新连接。

  Message Type   消息类型
  Message ID     PD Message ID
  CRC            Valid/Invalid/Unavailable
  Status         Complete/Partial/Invalid/Unsupported
  Summary        简短解析摘要

若方向或字段无法从现有数据模型可靠获取，应显示 `Unknown`
或留空，不能推断。

### 5.5 报文详情页面

建议采用三个区域：

1.  原始数据。
2.  协议字段树。
3.  诊断信息。

原始数据区展示：

-   原始字节。
-   十六进制视图。
-   按字段分组的字节范围（仅在偏移信息可靠时）。
-   原始 CaptureRecord 索引。

协议树展示：

``` text
PD Message
├── SOP
├── PD Header
│   ├── Message Type
│   ├── Data Role
│   ├── Power Role
│   ├── Specification Revision
│   ├── Message ID
│   └── Number of Data Objects
├── Extended Header（如适用）
├── Data Objects
│   ├── PDO / RDO
│   ├── VDM / VDO
│   └── Extended Payload
└── CRC
```

协议树中的字段必须来自解析结果。不要在 GUI 中重新计算字段含义。

### 5.6 PDO/RDO 专项视图

PDO 展示建议：

  字段          展示内容
  ------------- ---------------------------------------------
  PDO Index     能力序号
  PDO Type      Fixed/Variable/Battery/PPS/AVS 等已支持类型
  Min Voltage   最小电压
  Max Voltage   最大电压
  Current       电流能力
  Power         功率能力
  Raw Value     32 位原始值

RDO 展示建议：

-   选择的 PDO 序号。
-   Operating Current/Power。
-   Maximum Operating Current/Power。
-   GiveBack 等适用标志。
-   与当前有效能力对象的关联结果。
-   超范围和缺少上下文诊断。

要求：

-   保留原始十六进制值。
-   单位显示统一。
-   对部分解析结果明确标记。
-   不把能力通告等同于实际输出测量。

### 5.7 VDM/VDO 专项视图

展示：

-   Structured/Unstructured。
-   SVID。
-   Command。
-   Command Type。
-   Object Position。
-   Discover Identity 结果。
-   Discover SVIDs 列表。
-   Discover Modes 列表。
-   VDO 原始值和已解码字段。
-   VDMContext 请求/响应关联状态。

必须突出显示上下文诊断，例如：

-   `vdm_context_missing`
-   `vdm_discovery_response_mismatch`

对于 M7 实机中出现的 Identity ACK 缺少 DFP VDO、Modes 响应 SVID
与请求不一致等情况，应展示原始响应和诊断，不应将异常数据悄悄隐藏。

### 5.8 Extended/EPR 专项视图

展示：

-   Extended Message Type。
-   Data Size。
-   Chunked/Unchunked。
-   Chunk Number。
-   Request Chunk。
-   当前重组状态。
-   已接收分块。
-   缺失分块。
-   完整或部分 Payload。
-   EPR Source Capabilities。
-   SPR/EPR PDO 分类。
-   AVS/EPR 请求与能力关联。
-   上下文缺失和长度异常。

特别要求：

-   Chunked 消息显示分块进度。
-   未完成的消息显示 `Pending` 或 `Partial`。
-   不完整消息不得展示为完整 Payload。
-   未知扩展类型保留原始数据。
-   EPR 配置为 ON 不等于 EPR 能力已通告。
-   当前会话没有 EPR PDO 时，应显示"未观察到 EPR Source
    Capabilities/当前无有效 EPR PDO"，而不是显示"EPR 已启用"。

### 5.9 诊断页面

建议按级别分类：

-   Error：帧格式错误、长度冲突、CRC 错误等。
-   Warning：上下文缺失、请求/响应不匹配、部分数据等。
-   Info：未知类型、非关键状态和提示。

诊断表建议：

  字段          内容
  ------------- --------------------
  Severity      Error/Warning/Info
  Code          稳定诊断代码
  Frame Index   关联帧
  Timestamp     时间戳
  Message       人类可读说明
  Raw Data      原始数据引用

点击诊断应能定位到报文列表中的对应记录。

## 7. 数据保存和离线回放

### 7.1 捕获文件格式

第一版建议建立带版本号的项目原生捕获文件格式，至少保存：

-   软件版本。

-   原始 Binary Block 或可无损恢复的 CaptureRecord。

不应只保存 GUI 表格显示的摘要。

### 7.2 离线回放功能

第一版：

-   打开捕获文件。
-   显示文件元数据。
-   开始回放。
-   暂停和继续。
-   停止。
-   逐帧前进。
-   设置回放速度。
-   显示回放进度。
-   重新运行协议分析。

第一版不要求：

-   复杂时间轴缩放。

### 7.3 回放一致性

同一个原始捕获文件，在相同解析版本和配置下重复回放，应得到一致的单帧解析结果和上下文诊断。

当解析器版本变化时，应允许重新分析，并在结果中记录软件版本。

## 8. UI 性能与线程安全要求

### 8.1 主线程约束

以下操作不得在 GUI 主线程中执行：

-   阻塞式串口读取。
-   大文件读取。
-   大批量协议解析。
-   长时间 CRC/重组回放。
-   大量 CSV/JSON 导出。
-   长时间压力测试。

### 8.2 刷新策略

建议：

-   捕获线程批量提交数据。
-   UI 按固定刷新周期批量更新表格。
-   表格只保留必要的显示缓存。
-   原始记录可以按配置写入文件。
-   详情面板仅在选中记录变化时更新。
-   过滤和搜索采用模型/代理模型。

刷新周期和批量大小应通过实测确定，不应未经测试硬编码成过高刷新频率。

### 8.3 内存管理

-   区分原始捕获文件、内存记录缓存和表格显示缓存。
-   为内存捕获模式设置最大记录数。
-   提供"清空显示"与"清空本次捕获"不同操作。
-   清空显示不能误删已经保存的原始捕获文件。
-   大文件回放采用分批读取。
-   长时间运行监控内存和活动上下文数量。

### 8.4 UI 响应验收

建议工程目标：

-   普通页面切换无明显卡顿。
-   连接和断开期间界面保持响应。
-   实时捕获期间可以选择报文和查看详情。
-   大批量数据到达时不会因为逐帧创建控件而持续卡顿。
-   解析或回放发生异常时 GUI 不退出。
-   设备拔出后状态能够及时更新。

具体毫秒指标应在目标电脑上实测后确定。

## 14. 开发约束与风险控制

### 14.1 必须遵守的约束

1.  保留第二阶段协议解析层，不在 GUI 中重写协议规则。
2.  不改变 DRPD 原版固件数据帧格式。
3.  不在 GUI 主线程中执行阻塞式串口读取和大批量回放。
4.  有状态协议上下文必须按捕获顺序更新。
5.  不完整消息不得展示为完整消息。
6.  未知类型和异常帧必须保留原始数据。
7.  实机证据与 synthetic fixture 必须区分。
8.  不将 EPR 配置开关误判为 EPR 能力已通告。
9.  不因 UI 过滤而删除原始捕获数据。
10. 不允许缓冲区溢出后静默丢弃数据。
11. 保持现有电子负载功能兼容。
12. 任何协议层修复都必须补充纯 Python 回归测试。

### 14.2 主要风险

  风险                   影响                        处理措施
  ---------------------- --------------------------- ----------------------------------
  GUI 直接调用协议解析   UI 和协议层耦合             使用 AnalysisService
  串口读写阻塞主线程     界面卡死                    工作线程和信号槽
  每帧创建大量控件       长时间捕获卡顿              QTableView + Model
  高速数据积压           内存增长或丢帧              有界缓存、批量更新和明确过载状态
  跨帧上下文顺序错误     PDO/VDM/Extended 关联错误   单一有序分析入口
  任意帧回放             上下文不完整                第一版从文件头顺序回放
  原始数据保存不完整     无法复现问题                保存原始块或无损 CaptureRecord
  实机证据展示不准确     误导用户                    显示 real/synthetic/partial 状态
  现有电子负载功能回归   综合平台功能受损            P3.2 和 P3.8 执行专项回归

## 17. 本阶段最终目标

第三阶段的最终交付不是一个只能显示串口数据的调试窗口，而是一个能够完成以下工作的
USB-PD 协议分析上位机：

``` text
DRPD 硬件
    |
    v
USB CDC 实时捕获
    |
    v
原始 CaptureRecord
    |
    v
第二阶段协议解析引擎
    |
    v
Application Services
    |
    +------------------------------+
    |              |               |
    v              v               v
实时报文列表    协议详情树       诊断分析
    |              |               |
    +--------------+---------------+
                   |
                   v
          捕获保存 / 离线回放
                   |
                   v
             CSV / JSON 导出
```

**建议实施顺序：先完成 P3.0 仓库审查，确认现有主窗口、CDC
通信和协议层接口；再建立 Service
层和线程架构；随后开发实时捕获、协议详情和专项分析视图；最后完成离线回放、导出和实机验收。**

第三阶段完成后，项目将从"具备协议解析能力的开发工具"进一步发展为"具有实时捕获、可视化协议分析、离线复现和数据导出能力的综合测试软件"。
