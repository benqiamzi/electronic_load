### 3.2 状态定义

矩阵中的状态必须使用统一定义：

-   `real-verified`：有真实硬件捕获样本，并完成原始入口回放。
-   `synthetic-verified`：由明确标记的构造样本完成测试。
-   `partial`：已实现部分字段或存在不完整捕获。
-   `unsupported`：当前未实现语义解码。
-   `not-tested`：尚无足够测试证据。

一项功能可以同时拥有不同证据状态，例如"软件功能
synthetic-verified，实机覆盖
partial"。不能只用一个"已支持"标签掩盖证据差异。

## 4. 软件架构与回归范围

### 4.1 回归主链路

M7 的核心测试应覆盖完整数据路径：

``` text
DRPD 固件
    |
    v
USB CDC
    |
    v
原始 Binary Block
    |
    v
CaptureRecord
    |
    v
parse_capture(record)
    |
    +--------------------------+
    |                          |
    v                          v
普通 PD 消息                Extended Message
    |                          |
    v                          v
PDO / RDO / VDM             Extended Header
    |                          |
    v                          v
PDSessionContext          Reassembler
    |                          |
    v                          v
VDMContext                EPR 语义解析
    |                          |
    +-------------+------------+
                  |
                  v
           统一分析结果
                  |
                  v
          第三阶段 GUI 接口
```

### 4.2 架构约束

1.  `parse_capture(record)` 继续负责单条捕获记录解析。
2.  `PDSessionContext` 负责电源能力和请求关联。
3.  `VDMContext` 负责 VDM 发现信息。
4.  Extended Message Reassembler 负责跨帧分块重组。
5.  EPR 解析复用已有 PDO/RDO 解码逻辑。
6.  GUI 不得重新实现协议位域、CRC 或分块重组。
7.  原始捕获数据必须能够追溯到解析结果。
8.  重复解析同一记录时，纯解析结果应保持确定性。
9.  有状态上下文必须由明确的调用者管理，不能隐藏在单帧解析入口中。

### 4.3 M7 期间允许修改的代码

允许：

-   修复 M0--M6 回归中确认的问题。
-   补充边界诊断。
-   优化明显影响性能或内存的实现。
-   增加测试和 fixture。
-   完善文档和类型注释。
-   为 GUI 准备稳定的只读结果接口。

不允许：

-   无必要地重命名大量公共字段。
-   改变已验收字段的含义。
-   删除原始数据保留路径。
-   将状态管理迁入 GUI。
-   为了通过单个测试而放宽协议合法性检查。

### M7.4：性能和内存验收

#### 5.4.1 性能复测方法

必须复用 M6 的基准测试方法：

-   Windows。
-   Python 3.13.2。
-   4,000 次重组。
-   每次 260 B。
-   每次 10 个数据帧和 9 个反向请求帧。
-   SOP 与 SOP′ 交替。
-   计时包含 `parse_capture()`、CRC 和 `consume()`。
-   测试向量构造和串口读取不计入计时。
-   每次重组后核对 payload。
-   回放结束检查活动传输和缓存来源字节。

不得改变测试负载后直接与 M6
数字比较。若测试环境不同，应单独记录，不得声称与原基线完全等价。

#### 5.4.2 建议性能验收阈值

以 M6 基线为比较对象，建议 M7 在同一环境下满足：

  指标                       M6 基线             M7 建议验收值
  -------------------- ------------- -------------------------
  输入帧数                    76,000                      相同
  重组次数                     4,000                      相同
  平均吞吐               16,053 帧/s        不低于 14,448 帧/s
  平均单帧耗时              62.29 µs          不高于约 69.2 µs
  有效载荷吞吐           214.5 KiB/s          不低于基线的 90%
  `tracemalloc` 峰值      约 29.7 KB   同场景不高于基线的 125%
  回放后活动传输                   0                  必须为 0
  回放后缓存来源字节               0                  必须为 0

说明：

-   90% 吞吐和 125% 内存是本项目建议的工程验收容差，不是 USB-PD
    规范要求。
-   内存对比必须使用相同 Python 版本、测试脚本和输入规模。
-   `tracemalloc` 不代表进程全部实际内存，报告中应继续区分 Python
    跟踪分配和重组器来源字节计数。
-   若性能未达标，先定位耗时分布，不得通过删除
    CRC、跳过校验或丢弃原始数据来换取吞吐。

#### 5.4.3 补充性能场景

除 M6 原始基准外，增加：

-   纯普通 PD 帧解析。
-   VDM/VDO 解析。
-   单块 Extended Message。
-   多块 Extended Message 重组。

## 13. 本阶段最终目标

M7 的最终目标不是增加更多协议字段，而是证明现有 M0--M6
协议解析系统具备：

-   可重复的测试结果。

-   明确的协议支持边界。
-   稳定的上下文生命周期。

协议分析 GUI，而不再频繁修改底层协议模型。
